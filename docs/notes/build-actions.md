# GitHub Actions build research

Pinned sources: Dusklight `edf42c6a7202647b56dd2fcdef02d17671bc814b`; official mod template `ece6d0dae843675fbd1e3f2308a0f1f782da5d80`. Live [Dusklight Build runs](https://github.com/TwilitRealm/dusklight/actions/workflows/build.yml) include a successful main-branch run for `edf42c6` (#3480), so the selected SDK revision has upstream CI coverage. That game workflow builds the entire host, including separate macOS x86_64 and Windows x86_64 jobs; MidnaFX only needs the smaller mod-template workflow pattern.

## Relevant upstream contracts

- `upstream/mod-template/.github/workflows/build.yml` builds per-platform `.dusk` archives, uploads each, then downloads and merges them via `tools/merge_mod.py` and `symgen modmeta --check --update-json`. Its macOS Intel job runs on `macos-latest` with `-DCMAKE_OSX_ARCHITECTURES=x86_64`; Windows AMD64 uses an MSVC environment. Tag pushes produce a combined GitHub release. `upstream/mod-template/README.md` explicitly says a local single-platform `.dusk` should not be distributed as a cross-platform bundle.
- `upstream/dusklight/sdk/CMakeLists.txt` includes `cmake/ModSDK.cmake`. The latter's `_mod_download_link_stub` obtains a platform-specific version-independent link stub from `https://github.com/encounter/dusklight/releases/download/sdk`: `windows-amd64.lib` or `stub-macos-x86_64`, for these two targets. `DUSK_GAME_EXE` can supply a preexisting stub. The SDK fetches prebuilt Dawn through Aurora's `cmake/AuroraDawnProvider.cmake` for `FEATURES webgpu`; its default package URL is the `encounter/dawn` release using the Aurora-pinned Dawn version. No complete game build, game assets, or local ROM are needed.
- MidnaFX `CMakeLists.txt` demands the exact pinned Dusklight HEAD and its Aurora submodule. `upstream/` is gitignored, so CI must fetch Dusklight and initialize `extern/aurora` before configuring. `CMakePresets.json` provides `windows-release` (Visual Studio 18 2026) and `macos-intel-release` (Ninja, `CMAKE_OSX_ARCHITECTURES=x86_64`), but hosted `windows-latest` may not have VS 2026. Use a CI-specific Visual Studio generator available on the runner or Ninja after setting up MSVC, rather than assuming the local Windows preset works there.
- `upstream/mod-template/tools/merge_mod.py` requires identical non-library entries across input archives and distinct `lib/<platform>/` trees. It calls external `symgen` to check ABI/import metadata before writing a deterministic combined ZIP. `tools/check-package.py` in MidnaFX should verify each architecture package. The official template pins `SYMGEN_VERSION=v1.2.4` and downloads `symgen-linux-x86_64` from the corresponding GitHub release.

## Recommended MidnaFX workflow

Add `.github/workflows/build.yml` with minimal read permissions (`contents: read` on build jobs; only a release job receives `contents: write` if tag publishing is requested). Trigger on pushes to main, PRs, and manual dispatch; publish a release only on a version tag. Matrix jobs: `windows-latest` with MSVC amd64 and Ninja, and `macos-latest` with Ninja and explicit x86_64 target. Clone `TwilitRealm/dusklight` at the exact SHA, then `git submodule update --init --depth 1 extern/aurora`. Configure with the pinned checkout and platform settings, build, run `ctest`, inspect package layout, and upload `midnafx-windows-amd64.dusk` and `midnafx-macos-x86_64.dusk` as separate artifacts. This already removes manual builds for users; they choose their platform archive. A later merge job can reuse the template's `merge_mod.py` plus a version-pinned and integrity-verified `symgen` to produce one combined `.dusk` after both jobs pass.

Be careful with caches: cache only immutable Dusklight source by its commit plus OS, or use a fresh shallow fetch. Never cache `build/` across SDK revisions or architectures. Aurora and SDK download URLs are external dependencies; pin exact versions and verify release hashes before calling the resulting artifacts trusted releases. GitHub-hosted builds prove compile and package structure, not in-game loading, Metal correctness, visual parity, or latency on an Intel GPU. The macOS cross-architecture build should also use `file` or `lipo -archs` on the extracted module to assert x86_64.
